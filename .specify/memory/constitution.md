# dsh-task-lens 项目宪章

## 核心原则

### I. 状态真实优先
进度、完成、耗时和失败必须来自结构化任务事件或真实执行结果。不得根据流式输出长度推断完成度；AI 时间预测必须标识为估算，不能冒充承诺。

### II. 宿主能力优先
优先使用 DSH 的 Cordis 插件、Session 事件、右侧栏、浮窗、鉴权、会话分支与 LLM 服务。不得通过未公开 DOM 结构实现核心业务，不得另建绕过宿主权限的会话体系。

### III. 主对话隔离
子任务小窗的问答不得修改主会话任务状态、发送主对话消息或启动主代理新轮次。只有用户明确执行“提升为分支”后才创建分支；创建失败时原对话和小窗保持不变。

### IV. 测试先行
先为任务状态机、API 权限、上下文隔离和关键用户行为编写失败测试，再实现。每个公开行为至少有一个可执行验收测试；修复缺陷先复现。

### V. 简单且有界
MVP 只服务 DSH Web/桌面 Web 容器。任务数量、正文长度、上下文条数、请求并发和持久化数据必须有上限。避免通用工作流引擎、自动多代理编排和未经要求的平台抽象。

## 技术与安全约束

- 使用 TypeScript 严格模式、ESM、Node.js 24+、React 18 与 DSH 公开插件接缝。
- 所有 HTTP 请求先通过 `connection.requestRejection`；每次只能访问请求指定的一个 Session。
- 插件运行拥有 DSH 宿主权限，不声称工具审批能够沙箱化插件。
- 不把凭据、绝对本机路径或完整会话日志写入仓库；不引入遥测。
- 任务状态存储于 DSH Session 事件；小窗问答单独持久化并记录来源，不能混入主会话模型历史。
- 所有可见文案支持中文与英文；界面可用键盘操作，状态不只靠颜色表达。

## 交付与质量门

- PRD → 规格 → 计划 → 任务 → 实现 → 一致性检查，按 Spec Kit 流程维护。
- 提交前执行类型检查、单元/契约测试、构建和 `npm pack --dry-run`。
- README 必须给出安装、开发、权限范围、已知限制与实测范围。
- 未完成真实 DSH 验证时只能称为已通过本地自动化测试的 MVP，不宣称生产可用。

## 治理

本宪章约束所有规格与实现。变更原则时同步更新版本、日期、相关规格和测试；冲突以更严格的用户隔离与数据安全要求为准。
